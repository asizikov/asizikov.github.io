### Guardrails

Once you stop reviewing every edit, something else has to catch mistakes. Guardrails are the tools that give the agent fast, objective feedback: linters, formatters, type checkers, test suites, and browser tools like Playwright so it can actually look at the UI it built. The rule of thumb: if a requirement can be checked by a tool, don't put it in the instructions. A failing check is a much stronger signal than a sentence the model may or may not follow.

- Linters, formatters, CLI tools.
- Browser tools, Playwright: let the agent *see* what it built.
- Unit / e2e / acceptance tests as the agent's feedback signal.
- Deterministic checks > asking nicely in the instructions.

### Cross-checking with different models

Some problems can't be caught by a linter: a wrong assumption, a plan that misses the point, a subtle logic bug. A model reviewing its own work tends to agree with itself. Asking a different model to review the plan or the diff gives you a second set of blind spots, which in practice catches a surprising number of issues before a human ever looks.

- A second model reviews the first. Different blind spots.

### Complex flows: review, plan, gates

Longer tasks need structure. Instead of one prompt and a hope, you split the work into steps (plan, implement, review) and put a gate between them: a human approval, a passing test run, a reviewer agent's verdict. Custom agents give each step its own role, tools, and instructions, and workflows wire them together. See [Building and Testing Custom Agents](/2026/02/07/building-testing-custom-agents/) and [Dynamic Workflows: first look](/2026/10/03/dynamic-workflows-first-look/).

- Plan → implement → review, with gates between steps.
- Custom agents for specific roles.

### Memory

Every new session starts from zero. Memory lets the agent keep what it learned: a build quirk, a convention, a mistake not to repeat. Local memory stays with one developer or repository; shared memory spreads that knowledge across the team and every agent working on the code. It has the same weakness as instruction files: memory that is never pruned slowly turns into noise.

- Local: what this agent learned in this repo.
- Shared: what the team (and every agent) should know.
- Risk: memory going stale, same problem as instructions.



### Worktrees

Two agents in the same checkout will overwrite each other's work. Git worktrees give every session its own directory and branch on top of the same repository, so sessions can run side by side and each one ends as a clean, reviewable branch.

- Isolated checkout per session. No agents stepping on each other's files.

### Setup and cleanup scripts

A new worktree is an empty shell: no dependencies, no generated files, no local config. If a human has to prepare it, you've lost the point of parallel sessions. Setup scripts make a fresh worktree ready to build and test on its own, and cleanup scripts remove what it leaves behind.

- A fresh worktree must be ready to build in seconds, without a human.

### Port management

Every session that runs the app wants a dev server, and they can't all listen on port 3000. Ports have to be allocated per session and passed to the app, the tests, and the browser tools, so the agent checks *its own* instance and not someone else's.

- Five dev servers can't all listen on 3000.

### Databases and shared resources

Files are easy to isolate; state is harder. Sessions that share a database, cache, or test fixtures will break each other's tests in ways that look random. Either give each session its own copy (containers, per-session schemas, seeded fixtures) or coordinate access explicitly.

- Shared DB, caches, test fixtures. Isolate or coordinate.

### Automatic context management

Long sessions outgrow the context window, and at this scale nobody is there to start a fresh chat. The harness has to manage context on its own: compacting history, sending noisy sub-tasks to sub-agents, and splitting work into a parent session that plans and coordinates and child sessions that do the work.

- Compaction.
- Sub-agents.
- Child-parent (brain/hands) sessions: one session plans and coordinates, others execute.
